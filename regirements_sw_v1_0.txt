# 3. events.json – überwachte Events

Die zu überwachenden Veranstaltungen werden aktuell in:

```text
events.json
```

definiert.

Beispiel:

```json
[
  {
    "id": 1,
    "name": "Allgäu Triathlon",
    "sport": "Triathlon",
    "location": "Allgäu",
    "event_date": "2027-08-22",
    "official_url": "https://www.808project.de/allgaeutriathlon",
    "priority": "high"
  },
  {
    "id": 2,
    "name": "adidas INFINITE TRAILS 2027",
    "sport": "Trailrunning",
    "location": "Gastein Valley",
    "event_date": null,
    "official_url": "https://infinite-trails.com/en/",
    "registration_url": "https://infinite-trails.com/en/waitlist-2027/",
    "priority": "high"
  }
]
```

Die vollständige Datei enthält aktuell mehrere überwachte Veranstaltungen.

Die Architektur muss deshalb berücksichtigen:

```text
events.json
    │
    ├── Event-ID
    ├── Name
    ├── Sport
    ├── Location
    ├── Event-Jahr / Event-Datum
    ├── official_url
    ├── optional registration_url
    └── priority
```

Der Worker darf diese Eventdefinitionen nicht mit den erkannten Statusdaten verwechseln.

# 6. Fällige Events bestimmen

Es soll nur ein Event verarbeitet werden, wenn:

```text
next_check_at <= now
```

Beispielsweise:

```text
Event A
next_check_at = 20:05
→ prüfen

Event B
next_check_at = 22:00
→ noch nicht prüfen
```

Das ist wichtig, damit GitHub Actions zwar regelmäßig laufen kann, aber nicht jedes Event unnötig abgerufen wird.

# 8. AI-Analyse

OpenAI wird für die Analyse unstrukturierter Webseiten verwendet.

Die AI soll insbesondere erkennen:

* Registrierungsstatus
* Registrierungsbeginn
* Registrierungsende
* ungefähren Registrierungszeitraum
* Teilnehmerlimit
* Warteliste
* Ausverkauft
* konkrete Startzeit
* relevante Hinweise
* Event-Jahr

Wichtig:

## Keine Halluzinationen

Wenn auf einer Webseite steht:

> Registration opens in January.

darf daraus NICHT:

> Registration opens January 1.

gemacht werden.

Stattdessen:

```text
status = APPROXIMATE_DATE
approximate_registration_text = "Registration opens in January."
registration_start = null
```

Wenn eine Aussage nicht eindeutig ist:

```text
status = UNKNOWN
```

oder niedrige Confidence.

---

# 9. Event-Jahr zwingend berücksichtigen

Ein zentraler Fehler, der verhindert werden muss:

Eine Webseite kann Informationen über ein altes Event-Jahr enthalten.

Beispiel:

```text
Event auf der überwachten Liste:
IRONMAN Example 2027
```

Webseite:

```text
Registration opens January 10, 2026.
```

Diese Information darf nicht automatisch für das Event 2027 übernommen werden.

Die Analyse muss deshalb den Kontext berücksichtigen:

* Event-Jahr
* Event-Datum
* Registrierungsjahr
* Titel der Seite
* URL
* Seiteninhalt
* Kontext der gefundenen Aussage

Wenn nicht eindeutig feststeht, dass die Information zum überwachten Event gehört:

```text
UNKNOWN
```

oder entsprechend niedrige Confidence.

Dafür müssen passende Daten an `analyze()` bzw. die Analysepipeline übergeben werden.

# 10. Statusmodell

Das bestehende Statusmodell soll erhalten und vollständig unterstützt werden:

```text
ANNOUNCED
NOT_OPEN
APPROXIMATE_DATE
SCHEDULED
OPEN
LIMITED
WAITLIST
SOLD_OUT
CLOSED
CANCELLED
UNKNOWN
```

Bedeutung:

### ANNOUNCED

Event angekündigt, aber keine belastbare Information zum Registrierungsstatus.

### NOT_OPEN

Anmeldung definitiv noch nicht geöffnet.

### APPROXIMATE_DATE

Nur ungefährer Zeitraum bekannt.

Beispiel:

```text
Registration opens in January.
```

### SCHEDULED

Konkretes Registrierungsdatum bzw. Zeitpunkt bekannt.

### OPEN

Anmeldung geöffnet.

### LIMITED

Anmeldung geöffnet, aber begrenzte bzw. knappe Verfügbarkeit.

### WAITLIST

Nur Warteliste verfügbar.

### SOLD_OUT

Keine Plätze mehr verfügbar.

### CLOSED

Anmeldung geschlossen.

### CANCELLED

Veranstaltung abgesagt.

### UNKNOWN

Status kann nicht zuverlässig bestimmt werden.

# 12. Fakten und Vermutungen

AI-Ausgaben müssen zwischen:

```text
Fakt
```

und

```text
Vermutung
```

unterscheiden.

Eine Vermutung darf nicht als sichere Information in den Status übernommen werden.

Beispiel:

Webseite:

> Registration usually opens around January.

Nicht daraus machen:

```text
SCHEDULED
registration_start = January 1
```

sondern beispielsweise:

```text
APPROXIMATE_DATE
approximate_registration_text = "Registration usually opens around January."
```

# 15. ALARM- UND BENACHRICHTIGUNGSKONZEPT

Dies ist ein eigener wichtiger Arbeitsbereich.

Aktuell gibt es bereits einfache Sender für:

```text
Telegram
SMS / Twilio
E-Mail / SMTP
```

APNs ist für später vorgesehen.

Die bestehende Funktionalität soll analysiert und gezielt erweitert werden.

## Benachrichtigungsrelevante Ereignisse

Mindestens prüfen und unterstützen:

### Neues konkretes Öffnungsdatum

Beispiel:

```text
APPROXIMATE_DATE
        ↓
SCHEDULED
```

mit:

```text
Registration opens:
12.01.2027 10:00 CET
```

→ Alarm.

### Anmeldung geöffnet

```text
SCHEDULED
    ↓
OPEN
```

→ sofortiger Alarm.

### Verfügbarkeit wird knapp

```text
OPEN
    ↓
LIMITED
```

→ Alarm.

### Warteliste

```text
OPEN / LIMITED
    ↓
WAITLIST
```

→ Alarm.

### Ausverkauft

```text
OPEN / LIMITED / WAITLIST
    ↓
SOLD_OUT
```

→ Alarm.

### Anmeldung geschlossen

```text
OPEN
    ↓
CLOSED
```

→ relevante Benachrichtigung.

### Veranstaltung abgesagt

```text
*
 ↓
CANCELLED
```

→ wichtige Benachrichtigung.

### Rückkehr zu einem anderen Status

Auch ungewöhnliche Statusänderungen müssen verarbeitet werden, ohne dass der Worker abstürzt.

# 16. Deduplizierung von Alarmen

Der Worker läuft möglicherweise alle 30 Minuten.

Deshalb darf bei folgendem Zustand:

```text
OPEN
```

nicht alle 30 Minuten erneut dieselbe Nachricht versendet werden.

Es muss zwischen:

```text
Status wurde gerade geändert
```

und:

```text
Status ist weiterhin unverändert
```

unterschieden werden.

Eine Benachrichtigung soll nur einmal pro relevanter Statusänderung erfolgen, sofern keine bewusste Wiederholung/Eskalation vorgesehen ist.

---

# 17. Benachrichtigungsprotokoll

Der Worker soll nachvollziehbar speichern können:

```text
wann
für welches Event
welcher Status
welcher Kanal
welche Nachricht
erfolgreich / fehlgeschlagen
Fehlermeldung
```

Dabei die bestehende Architektur nutzen.

Nicht einfach ein völlig neues Datenbanksystem einführen.

Da aktuell `status.json` verwendet wird, prüfen, welche Informationen dort sinnvoll und dauerhaft gespeichert werden können.

# 18. Nicht konfigurierte Kanäle

Wenn beispielsweise Telegram nicht konfiguriert ist:

```text
TELEGRAM_BOT_TOKEN fehlt
```

darf das nicht wie ein echter Versandfehler behandelt werden.

Unterscheide:

```text
Kanal nicht konfiguriert
```

von:

```text
Kanal konfiguriert, Versand fehlgeschlagen
```

Nicht konfigurierte optionale Kanäle sollen den gesamten Worker nicht als fehlgeschlagen erscheinen lassen.

---

# 19. Fehler und Retry

Wenn ein konfigurierter Kanal einen Fehler liefert:

```text
Telegram API Fehler
SMTP Fehler
Twilio Fehler
```

soll der Fehler sauber protokolliert werden.

Die Benachrichtigungslogik soll nicht den kompletten Monitoring-Lauf abbrechen.

Prüfe, ob eine sinnvolle Retry-Strategie erforderlich ist.

Keine endlosen Retries.

# 21. Monitoring-Frequenz

Das Monitoring soll dynamisch über:

```text
next_check_at
```

gesteuert werden.

Grundidee:

```text
> 6 Monate bis Event
→ ca. 1x pro Woche

3–6 Monate
→ alle 2–3 Tage

1–3 Monate
→ 1x täglich

< 30 Tage
→ alle 2 Stunden

Registrierung innerhalb 48 Stunden
→ beim nächsten 30-Minuten-Lauf

OPEN oder LIMITED
→ beim nächsten 30-Minuten-Lauf
```

GitHub Actions läuft in dieser Arbeitsphase technisch ungefähr alle 30 Minuten.

Aber:

> Nicht jedes Event bei jedem Lauf abrufen.

Nur:

```text
next_check_at <= now
```

prüfen.

# 32. Bewertung und verbindliche Präzisierungen

## Verständlichkeit

Die Anforderungen sind fachlich verständlich und beschreiben das gewünschte Verhalten ausreichend. Die Alarmierung und Benachrichtigung ist jetzt als eigener Arbeitsbereich enthalten.

Für die Umsetzung müssen die folgenden Punkte verbindlich gelten:

## Umsetzbarkeit

Die Anforderungen sind mit der bestehenden Architektur umsetzbar. Die Umsetzung soll schrittweise erfolgen und zunächst bei `events.json`, `status.json` und GitHub Actions bleiben. Eine PostgreSQL-Migration ist dafür nicht erforderlich.

## Verbindliche technische Regeln

### Benachrichtigungsprotokoll

Da `status.json` aktuell der dauerhafte Statusbestand des Workers ist, muss die Lösung festlegen, wo der Versandstatus gespeichert wird. Mindestens erforderlich ist eine strukturierte Historie pro Alarm mit:

```text
event_id
transition_key
channel
message_type
attempted_at
success
error
```

Der vollständige Nachrichtentext darf nur gespeichert werden, wenn dadurch keine vertraulichen Daten öffentlich über GitHub Pages bereitgestellt werden.

### Deduplizierung

Eine Deduplizierung darf nicht ausschließlich auf `event_id + old_status + new_status` basieren. Ein Event kann beispielsweise mehrfach zwischen `OPEN` und `LIMITED` wechseln.

Der `transition_key` muss deshalb zusätzlich eine Beobachtung oder einen Content-Hash berücksichtigen. Derselbe unveränderte Seiteninhalt darf keine erneute Nachricht erzeugen; eine später erneut belegte Statusänderung muss dagegen alarmierbar bleiben.

### Kanalstatus

Jeder Kanal muss mindestens einen der folgenden Zustände liefern:

```text
NOT_CONFIGURED
SENT
FAILED
```

`NOT_CONFIGURED` ist kein Monitoringfehler. `FAILED` gilt nur für einen konfigurierten Kanal, dessen Versand technisch fehlgeschlagen ist.

### Fehlerbehandlung und Retry

Ein Fehler in einem Kanal darf weder die Verarbeitung des Events noch andere Kanäle abbrechen. Retries müssen begrenzt sein und dürfen bei jedem GitHub-Actions-Lauf nicht automatisch dieselbe Nachricht erneut versenden.

### Benachrichtigungsinhalt

Eine Nachricht darf nur Werte aus der aktuellen, belegten Beobachtung verwenden. Wenn Quelle, Evidence, Event-Datum oder Registrierungsbeginn nicht bekannt sind, müssen diese Felder weggelassen oder ausdrücklich als unbekannt gekennzeichnet werden.

### Quellenfeld

Der Feldname wird einheitlich als `source_url` verwendet. Die abweichende Schreibweise `sources_url` in Abschnitt 26 ist zu korrigieren.

## Abnahmekriterien

Die Alarmierungsanforderung gilt erst als umgesetzt, wenn mindestens folgende Fälle automatisiert getestet sind:

1. Jeder relevante Statuswechsel erzeugt höchstens einen Alarm pro belegter Beobachtung.
2. Ein unveränderter Status erzeugt bei wiederholten Worker-Läufen keinen neuen Alarm.
3. Ein Wechsel `OPEN -> LIMITED -> OPEN -> LIMITED` kann bei jeder neuen belegten Änderung erneut alarmieren.
4. Ein nicht konfigurierter Kanal wird als `NOT_CONFIGURED` protokolliert und lässt den Lauf erfolgreich bleiben.
5. Ein Fehler eines konfigurierten Kanals wird als `FAILED` protokolliert und lässt die übrige Verarbeitung weiterlaufen.
6. Die Nachricht enthält Status, Event, Quelle und Evidence nur dann, wenn diese Informationen tatsächlich vorhanden sind.
7. `CANCELLED` erzeugt unabhängig vom vorherigen Status eine wichtige Benachrichtigung.

## Ergebnis der Analyse

```text
Verständlichkeit: gut, nach den Präzisierungen eindeutig
Technische Umsetzbarkeit: ja, ohne PostgreSQL-Migration
Größtes Risiko: dauerhafte Alarmhistorie und korrekte Deduplizierung in status.json
Nächster Umsetzungsschritt: Ist-Zustand der bestehenden Notification-Funktionen testen und danach die Alarmhistorie erweitern

# 33. Kostenfreie Dienste als Randbedingung

Die Standardlösung soll ohne laufende Kosten nutzbar sein.

## Kostenfreie Standardkanäle

- Telegram Bot API
- E-Mail über einen vorhandenen kostenlosen SMTP-Anbieter oder ein vorhandenes E-Mail-Konto
- GitHub Actions und GitHub Pages innerhalb der jeweils geltenden kostenlosen Kontingente

## Kostenpflichtige Optionen

- Twilio-SMS ist nicht grundsätzlich kostenlos und darf deshalb nur optional aktiviert werden.
- OpenAI API ist nicht grundsätzlich kostenlos. Für einen vollständig kostenlosen Betrieb muss eine lokale oder anderweitig kostenfreie Analyse verwendet werden.
- PostgreSQL-Dienste wie Supabase, Neon oder Railway dürfen nur innerhalb eines dauerhaft kostenlosen Kontingents eingesetzt werden und sind für den aktuellen Worker nicht erforderlich.

Nicht konfigurierte kostenpflichtige Dienste dürfen den kostenlosen Standardbetrieb nicht verhindern. Telegram und E-Mail sollen als primäre kostenfreie Benachrichtigungskanäle verwendet werden.

# 34. Telegram-Laufzusammenfassung

Nach jedem abgeschlossenen Worker-Lauf soll der Telegram-Bot eine Zusammenfassung senden.

Die Zusammenfassung muss mindestens enthalten:

```text
Laufnummer, sofern vorhanden
Anzahl geprüfter Events
Anzahl erfolgreicher Prüfungen
Anzahl fehlgeschlagener Prüfungen
aktuelle Statusverteilung
Fehlerdetails für höchstens fünf fehlgeschlagene Events
```

Die Laufzusammenfassung ist von einzelnen Statusalarmen getrennt. Sie wird bei jedem Lauf höchstens einmal versendet und darf nicht durch die Deduplizierung von Statusalarmen unterdrückt werden. Wenn Telegram nicht konfiguriert ist, bleibt der Monitoring-Lauf trotzdem erfolgreich.
